# 集計SQLの万能レシピ

対象読者: SQL・BigQueryを学び始めて1ヶ月の自分。
目的: **どんな集計問題が来ても、同じ手順を上から実行すれば設計図とSQLに辿り着ける**ようにする。

## 大原則: SQLは「書く」ものではなく「組み立てる」もの

- 問題文を読んで、いきなり `select` を書き始めない。**設計図(ステップ1〜4)が埋まるまでSQLを書くのは禁止**
- SQLは「表を別の表に変換する機械」。だから最初にやることはSQLの文法ではなく、**入口の表と出口の表を紙に描くこと**
- 過去の失敗は、ほぼすべて「設計図を描かずに書き始めた」ことが原因(SQL力の問題ではない)

# 第1部: 問題文からSQLまでの6ステップ(アドホック分析はここから)

## ステップ1: 問題文に線を引いて「4つの部品」に分解する

どんな集計の問題文も、必ずこの4つの部品でできている。問題文に線を引いて仕分ける:

| 部品 | 見つけ方(問題文のこの言葉を探す) | SQLでの正体 |
|---|---|---|
| **軸** | 「〜別に」「〜ごとに」 | GROUP BYに並べる列 |
| **メジャー** | 「売上」「UU」「回数」「平均」 | SUM / COUNTの中身 |
| **母集団** | 「〜したユーザーが」「〜な人の」 | WHERE / JOINによる**絞り込み** |
| **時点・期間** | 「〜月に」「〜時点の」「過去N日」 | 日付のWHERE条件 |

### issue #25でやってみる

> 「**新規ユーザーが** / **登録月に** / **最初に購入した** / **商材別** / **売上**(と新規UU)」

- **軸**: 月 × 商材名
- **メジャー**: 売上(円を足す)、新規UU(人を数える)
- **母集団**: 「登録した月のうちに、人生で最初の購入をしたユーザー」の「その最初の購入明細」**だけ**
- **時点・期間**: 「登録月 = 初回購入の月」という一致条件

### 「母集団」がこのレシピで一番大事な新部品

日次KPIのような「全員を数える」問題では意識しなくてよかったが、**アドホック分析は「誰を対象に入れるか」の絞り込みこそが問題の本体**であることが多い。
「新規ユーザー」「離脱ユーザー」「課金経験者」のような言葉が出てきたら、**その定義(何をもってそう呼ぶか)を日本語で1文書けるまで先に進まない**こと。

- 例: 新規ユーザー = 「`users.created_at`(登録日)の属する月の中に、人生初の購入をした人」
- 定義に迷ったら: 出題者に聞く/ヒント資料を見る/自分で決めてコメントに残す、のどれかを必ずやる

**この分解で問題の8割が終わる。** issue #25の最初の実装の誤り(登録月の欠落・初回購入の欠落・新規判定の取り違え)は、全部このステップを飛ばしたことで起きた。

## ステップ2: 完成形の表を「具体的な値で」3行描く

頭の中ではなく、実際に描く。値はでっち上げでいい:

| month | product_name | sales | new_user_uu |
|---|---|---|---|
| 2025-10-01 | Tシャツ | 12,000 | 3 |
| 2025-10-01 | スニーカー | 8,500 | 2 |
| 2025-11-01 | Tシャツ | 4,000 | 1 |

描いたら「**1行 = 何か**」を一言で言う:

> 1行 = ある月に登録した新規ユーザーのうち、初回購入の商材がこれだった人たちの合計

言えなければステップ1に戻る。この「1行=何か」を**グレイン**と呼ぶ。

## ステップ3: 集計する直前の表(材料表)を具体的な値で描く

完成形から逆算する。ルールは1つ: **メジャーの数える単位(円・人)が、1行に1個ずつ乗っている形**にする。

- 売上を足すなら → 1行に `sales_jpy` が1個
- UU(人)を数えるなら → 1行に `user_id` が1個(最後まで殺さず運ぶ)

issue #25の材料表(1行 = 母集団ユーザー1人の初回購入明細):

| user_id | month(登録月) | product_name | sales_jpy |
|---|---|---|---|
| 101 | 2025-10-01 | Tシャツ | 4,000 |
| 102 | 2025-10-01 | Tシャツ | 8,000 |
| 103 | 2025-10-01 | スニーカー | 3,500 |

**この表さえ作れれば、最後は `group by month, product_name` + `sum` + `count(distinct user_id)` するだけ。**
つまりSQLの問題は「この材料表をどう作るか」に置き換わった。

## ステップ4: 材料表の各列の「出どころ」を埋める

列を1つずつ取り上げて、**固定の4つの質問を上から順に**当てる。YESになったところで手段が確定する:

```
Q1. この列、既存のどこかのモデルに「そのまま」入っているか?
 ├ YES → そのモデルのグレイン(1行=何か)を確認:
 │        ・材料と同じ粒度 → そのままJOINで横に貼る
 │        ・材料より細かい(明細など) → 材料の粒度まで集計してからJOIN
 │        ・材料より粗い(ユーザー1行のマスタなど) → JOINすると各行に配られる
 └ NO → Q2へ
Q2. 「同じ行の中にある別の列」だけから計算できるか?
 ├ YES → CASE / IF / 四則演算で導出
 └ NO → Q3へ
Q3. 「同じテーブルの別の行」(過去・未来・同じユーザーの他の行)を見れば分かるか?
 ├ YES → ウィンドウ関数(LAG / LEAD / SUM OVER / ROW_NUMBER)
 └ NO → Q4へ
Q4. プロジェクトのどこにもない
 └ → データレイク(source)から新しいstagingを作って持ってくる
```

Excelでイメージすると: 土台のFROM=行を並べる / JOIN=**VLOOKUP** / CASE=行内の**IF式** / ウィンドウ=**上下の行を参照する式**。

**土台の選び方**: 「材料と同じグレインで、欲しい母集団の行を過不足なく持っているモデル」を土台にする。無ければ、土台自体を加工して作る(下のissue #25では「初回購入明細」という土台を自分で作っている)。

issue #25の出どころ表:

| 材料の列 | 質問の結果 | 手段 |
|---|---|---|
| user_id, product_name, sales_jpy | Q1: `int__cleansed_orders` にある。ただし「全購入」なので**初回の1件に絞る加工**が要る | Q3: 同じユーザーの他の行との比較 → `row_number()` |
| 登録月 | Q1: NO → Q4: データレイク由来の `stg__users.created_at` | ユーザー1行のマスタ → JOIN |
| (母集団の条件)登録月=初回購入月 | Q2: 上の2列が揃えば行内で比較できる | WHERE |

## ステップ5: 日本語 → SQL対訳表

設計図をSQLに変換するとき、問題文・設計図の言葉をこの表で引く:

| 問題文・設計図の言葉 | SQLの型 |
|---|---|
| 「Aごとに / A別に」 | `group by A` |
| 「AにBの情報を付ける」 | `left join B on キー`(Bが1行=1キーであること) |
| 「人生で最初の / 最後の1件」 | `row_number() over (partition by user_id order by 時刻 [desc])` を付けて `qualify ... = 1` |
| 「〜した人だけ」 | `where 条件`、または該当者だけのCTEを作ってJOIN |
| 「〜時点の累計」 | `where 日付 < '時点'` してから `sum` |
| 「過去N日間の」 | `sum() over (order by unix_date(date) range between N preceding and 1 preceding)` |
| 「人数(UU)」 | `count(distinct user_id)`(※行数を数える `countif` と混同しない) |
| 「条件を満たす行数」 | `countif(条件)` |
| 「AとBが同じ月」 | `date_trunc(A, month) = date_trunc(B, month)` |
| 「グループ内で全行同じ値を1個だけ取る」 | `any_value(x)` |
| 「グループ内でyが最大の行のx」 | `any_value(x having max y)` |
| 「UTCの日時を日本時間の日付に」 | `date(datetime(created_at, "Asia/Tokyo"))` |

## ステップ6: CTEを1個ずつ、実行しながら積む(一気に書かない)

**全文を書き上げてから初めて実行する、をやめる。** 作業ルール:

1. **CTEを1個書くたびに、末尾を `select * from そのCTE` にして実行**し、目で見る
   ```bash
   venv/bin/dbt compile --select <ファイル名(拡張子なし)>
   venv/bin/dbt show --inline "$(cat target/compiled/dbt_hands_on/analyses/<ファイル名>.sql)" --limit 10
   ```
   ※ SQL側に `limit` を書かないこと。`dbt show` は末尾に自分のLIMITを常に追記するため、SQLにlimitがあると二重になって構文エラーになる。件数は `--limit` オプションで渡す
2. 各CTEの直上に `-- 1行 = ◯◯` コメントを書く。**書けないCTEは設計がまだ**ということ
3. **JOINを書いたら、直前のCTEと件数を比べる**(`select count(*)`)。増えていたら相手のグレイン確認漏れ(distinct忘れ・キー不足)
4. 全部のCTEが確認できてから、最後の集計SELECTを書く

エラーは出る前提でいい。1CTEずつ確認していれば「どこで壊れたか」が常に1箇所に絞れる。全文を書いてから実行すると、構文エラー・参照エラー・設計ミスが同時に出て、どこから直せばいいか分からなくなる。

## issue #25 完全ワークスルー(ステップ1〜6を通す)

```sql
-- ステップ1の分解メモ:
--   軸: 登録月 × 商材名 / メジャー: 売上(円)・新規UU(人)
--   母集団: 登録月中に人生初の購入をしたユーザーの、その初回購入明細
with

-- 1行 = 1ユーザー(登録日付き)
users as (
    select
        id as user_id,
        date(datetime(created_at, "Asia/Tokyo")) as registered_date
    from {{ ref("stg__users") }}
),

-- 1行 = 1ユーザーの「人生最初の購入明細」1件
first_purchases as (
    select user_id, order_time_jst, product_name, sales_jpy
    from {{ ref("int__cleansed_orders") }}
    qualify row_number() over (
        partition by user_id
        order by order_time_jst, order_id, inventory_item_id  -- 同時刻タイの順序も固定する
    ) = 1
),

-- 1行 = 母集団ユーザー(登録月に初回購入した人)の初回購入明細+登録月
new_user_first_purchases as (
    select
        date_trunc(users.registered_date, month) as month,
        first_purchases.user_id,
        first_purchases.product_name,
        first_purchases.sales_jpy
    from first_purchases
    join users using (user_id)
    where date_trunc(date(first_purchases.order_time_jst), month)
        = date_trunc(users.registered_date, month)   -- 「登録月に」の条件
)

-- 最後に1回だけ集計(材料表→完成形)
select
    month,
    product_name,
    sum(sales_jpy) as sales,
    count(distinct user_id) as new_user_uu
from new_user_first_purchases
group by month, product_name
```

**自分で決めてコメントに残すべき定義**(正解は1つではない):
1. 「最初に購入した商材」の単位 — 上の実装は明細1件(同時刻タイは `order_id, inventory_item_id` 順で固定)。「初回**注文**の全明細」を対象にする定義もあり得る
2. 「商材名」の粒度 — `product_name`(商品名、数万種)か `product_category`(カテゴリ)か

# 第2部: dbtモデル開発編(YAMLメタ情報がある場合)

作るものがアドホックではなくdbtモデルで、**YAML(カラム定義)が先にある**場合は、ステップ1の代わりに「D/M仕分け」から入る。以降のステップは第1部と同じ。

## ステップ1': YAMLのカラムをD(ディメンション)とM(メジャー)に仕分ける

判定基準は1つ: 「**この列はsum/countで潰せるか?**」潰せない列がD(=軸)、潰した結果の列がM。

`mart__daily_kpis` で実際にやった仕分け:

| カラム | D/M | 判定理由 |
|---|---|---|
| date | **D** | DATE型。日付をsumしても意味がない |
| detail_user_type | **D** | STRING型の分類ラベル |
| past_d30_payment_segment | **D** | STRING型の分類ラベル |
| dau, new_uu, ..., payment_uu | M | 「〜uu」=ユーザーを数えた結果 |
| sales | M | 円を足した結果 |

**グレイン = D列の全部の組み合わせ**。「潰せない列がある」こと自体がグレインの証拠になる(このプロジェクトでは、これで課題資料のdate uniqueテストが誤りだと判定できた)。

## メジャーごとの「数える単位」→ SQLの対応表

| メジャー | 数える単位 | SQL |
|---|---|---|
| dau | ユーザー | `count(distinct user_id)` |
| new_uu | ユーザー(材料が1行=1ユーザーのとき) | `countif(detail_user_type = '新規')` |
| d1_access_uu | ユーザー(0/1フラグ) | `sum(d1_access_flg)` |
| payment_uu | ユーザー(条件付き) | `count(distinct if(sales > 0, user_id, null))` |
| sales | 円 | `sum(sales)` |

ここで「集計直前の行に **user_id が生き残っていなければならない**」という制約が判明する。先に日付だけでGROUP BYしてuser_idを潰すと、UUは二度と数えられない。

## 材料の粒度の公式と、GROUP BYで畳まれる様子

> 材料の粒度 = 出力のD列がすべて決まり、かつ数える単位のキーが1行に1個乗っている粒度

daily_kpisなら材料は「ユーザー×日」。この4行が:

| user_id | date | detail_user_type | segment | sales |
|---|---|---|---|---|
| 101 | 1/10 | 新規 | h_0円 | 0 |
| 102 | 1/10 | 既存課金経験 | g_1円~1,000円 | 800 |
| 103 | 1/10 | 既存課金経験 | g_1円~1,000円 | 0 |
| 101 | 1/11 | 既存無課金 | h_0円 | 0 |

GROUP BYでこう畳まれる(102と103は3軸が同じ値なので同じ行へ):

| date | detail_user_type | segment | dau | sales |
|---|---|---|---|---|
| 1/10 | 新規 | h_0円 | 1 | 0 |
| 1/10 | 既存課金経験 | g_1円~1,000円 | **2** | 800 |
| 1/11 | 既存無課金 | h_0円 | 1 | 0 |

**グレインとは「誰と誰が同じ行に入るか」の決め事**だと、この変換を見れば分かる。

## なぜ「集計は最後に1回」なのか — 悪い例

「先に日付ごとの売上を集計して、あとでユーザー行にJOINで配る」と:

```
日次売上(先に集計): 1/10 → 800円
ユーザー×日の3行(101,102,103)にJOINすると、3行全部に800が乗る
最後にsumすると 2,400円(正解は800円)
```

> **鉄則: 集計は最後に一度だけ。途中でやりたくなったら、それは材料の粒度がまだ揃っていないサイン。**

例外は「材料作りのための中間集計」のみ(しきい値判定用の別グレインUU集計、過去売上ウィンドウ、ユーザー×月への事前集計など)。それも必ず材料表に戻して(JOINして)から最後の集計に合流する。

## モデルの2類型(集約型と付与型)

| 型 | グレインの変化 | 主な道具 | 最後の工程 | 例 |
|---|---|---|---|---|
| **集約型** | 細→粗(潰す) | GROUP BY | GROUP BY+集計関数 | mart__daily_kpis、mart__daily_sales |
| **付与型** | 保つ(潰さない) | ウィンドウ、JOIN、CASE | 属性導出のSELECT | int__daily_registered_user_types、int__cleansed_orders |

- YAMLに「数えた結果」の列(〜uu等)が無ければ付与型のサイン。**材料の粒度=出力グレインとなり、最後のGROUP BYが消える**
- ハイブリッドもある: int__daily_user_sales は「①GROUP BYで日次売上を確定(集約)→②ウィンドウで過去売上を付与→③CASEでセグメント導出」の3段。**グレインを変えるのは①の1箇所だけ**

## コメントテンプレート

モデルファイルの冒頭にこれを書いてから実装する:

```sql
-- 出力グレイン: 日付 × 詳細ユーザータイプ × 課金セグメント
-- メジャーの数える単位: ユーザー(dau, uu系) / 円(sales)
-- 母集団: アクセスした登録ユーザー全員(絞り込みなし)
-- 材料の粒度: ユーザー×日
-- 材料の揃え方: int__daily_registered_user_types ⟕ int__daily_user_sales (user_id, date)
-- 集計: 最後に1回、3軸でGROUP BY
```

## このプロジェクトでの適用例

| モデル | 型 | 材料の粒度 | 最後の軸 |
|---|---|---|---|
| mart__daily_sales | 集約型 | 注文明細 | 日付 |
| mart__monthly_department_brand_sales | 集約型(+中間集計) | 注文明細(+ブランド付替え) | 月×タイプ×部門×ブランド |
| mart__daily_kpis | 集約型 | ユーザー×日 | 日付×詳細タイプ×セグメント |
| mart__monthly_kpis | 集約型(+中間集計) | ユーザー×月 | 月×国 |
| int__monthly_registered_user_types | 集約型 | ユーザー×日 | ユーザー×月 |
| int__daily_registered_user_types | 付与型 | ユーザー×日(=出力) | なし |
| int__daily_user_sales | ハイブリッド | ユーザー×日 | ①のみGROUP BY |

## 関連する落とし穴(このプロジェクトで実際に踏んだもの)

- **UU(distinct count)は加法性がない** — 分類を付け替えたら必ず数え直す。UU同士を足してはいけない。ただし「同じ粒度の行を重複なく分割する軸」で分けたUUは、合算すると全体UUに一致する(BIで再集約できる設計の根拠)
- **ROWSは行数、RANGEは値の距離** — 「過去30日」はカレンダー日なので `order by unix_date(date)` + `range between 30 preceding and 1 preceding`。ROWSだとアクセス日の飛びで窓がずれる
- **ウィンドウSUMのNULL** — 過去に行がなければ0ではなくNULL。`coalesce(..., 0)` で畳んでから判定する
- **`count(distinct ...)` はウィンドウ関数では使えない** — GROUP BYで先に数えてJOINで戻す。または `any_value(x having max y)` で代替できる場合もある
- **`percentile_cont` のOVERにORDER BYは書けない** — PARTITION BYのみ。グループ内全行同値になるので最後は `any_value` で潰す
- **SELECTの別名はWHEREでは使えない** — WHEREはSELECTより先に評価される。元の式で書く(GROUP BY/ORDER BY/QUALIFYでは使える)
- **WHEREはJOINを全部書き終えた後に置く** — FROM句の途中には書けない
- **JOINの使い分け** — ファクトの必須構成要素(ヘッダ×明細)はINNER、ディメンション付与(マスタ参照)はLEFT。「相手が欠けたとき、行を消すべきか、NULLで残すべきか?」で判定する
- **`countif(条件)` は行数、`count(distinct if(条件, キー, null))` はユニーク数** — 別物
- **テーブルに並び順という概念はない** — CTE内のorder byは無意味。並びは読むクエリの最外側で指定する
- **CTEはWITHを1回書いてカンマでつなぐ** — CTE間のカンマ欠落・最後のCTE後の余分なカンマはどちらも構文エラー
- **アクセスベースと登録ベースの「新規」は別物** — このデータではevents/ordersの日付が整合しないため、購入分析にアクセス由来のuser_typeを使うとほぼNULLになる。ユーザー属性起点の分析は `stg__users.created_at`(登録)を基準にする
