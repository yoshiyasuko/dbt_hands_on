# 集計モデルの万能レシピ

dbtで集計モデル(mart・集計系intermediate)を作るときに、SQLを書き始める前に必ず回す手順。
このドキュメントは `mart__daily_kpis` を題材に、**各ステップで実際に何を書き、何ができあがるのか**を具体的に追う。

## 全体像を3行で

1. **完成形の1行が何か**を確定する(=グレイン)
2. その1行を作るのに**必要な材料の行が何か**を逆算する
3. 材料を全部並べ終えてから、**最後に1回だけ**集計する

料理と同じで、「盛り付け(GROUP BY)は最後に1回。途中でフライパンの中身を皿に盛り始めたら失敗」という手順。

---

## ステップ0: 集約型か付与型かを判定する

最初にYAML(メタ情報)を見て、**メジャー(数える対象)があるか**を確認する。

| 質問 | Yes → | No → |
|---|---|---|
| カラムに `~uu` / `~count` / `sales` のような「数えた結果」があるか? | **集約型**(行を潰す。ステップ1〜5を全部回す) | **付与型**(行を潰さない。ステップ5が消える) |

- 集約型の例: `mart__daily_kpis`(dau, sales…を数える)、`mart__daily_sales`
- 付与型の例: `int__daily_registered_user_types`(1行=ユーザー×日のまま、user_typeやフラグという**属性を足す**だけ)、`int__cleansed_orders`

---

## ステップ1: 出力のグレインを宣言する

**やる作業**: YAMLのカラムを1つずつ「D(ディメンション=切り口)」「M(メジャー=数える対象)」に仕分ける。
判定基準は1つだけ——「**この列はsum/countで潰せるか?**」。潰せない列がD、潰した結果の列がM。

`mart__daily_kpis` のYAMLで実際にやるとこうなる:

| カラム | D/M | 判定理由 |
|---|---|---|
| date | **D** | DATE型。日付をsumしても意味がない=潰せない |
| detail_user_type | **D** | STRING型の分類ラベル。潰せない |
| past_d30_payment_segment | **D** | STRING型の分類ラベル。潰せない |
| dau | M | 「〜uu」=ユーザーを数えた結果 |
| new_uu 〜 d1_14_access_uu | M | 同上 |
| payment_uu | M | 同上 |
| sales | M | 円を足した結果 |

**成果物**: グレイン宣言の一文。**グレイン=D列の全部の組み合わせ**なので:

> 1行 = 「ある日の、ある詳細ユーザータイプの、ある課金セグメント」のユーザー群

### このステップで実際に踏んだ罠

課題文には `date` にuniqueテストを付けろとあった。しかしYAMLに `detail_user_type` という**潰せない列**が存在する時点で、グレインは日付単独ではあり得ない(日付だけがグレインなら、detail_user_typeの値を1行に決められない)。**「潰せない列がある」こと自体がグレインの証拠**であり、課題のuniqueテストの方が誤りだと判定できた。

## ステップ2: メジャーの「数える単位」を特定する

**やる作業**: ステップ1でMにした列それぞれに「何を数えるのか」を書き足す。

| メジャー | 数える単位 | SQLでの姿(ステップ5で使う) |
|---|---|---|
| dau | **ユーザー**を数える | `count(distinct user_id)` |
| new_uu | ユーザーを数える(新規だけ) | `countif(detail_user_type = '新規')` ※1行=1ユーザーになっている前提 |
| d1_access_uu 等 | ユーザーを数える(フラグ=1だけ) | `sum(d1_access_flg)` ※フラグが0/1だからsumで数えられる |
| payment_uu | ユーザーを数える(その日購入した人だけ) | `count(distinct if(sales > 0, user_id, null))` |
| sales | **円**を足す | `sum(sales)` |

**このステップの存在意義**: ここで「集計直前の行に **user_id が生き残っていなければならない**」という制約が判明する。
アンチ例: 先に日付だけでGROUP BYしてuser_idを潰してしまうと、そのあと何をどうJOINしてもUUは二度と数えられない。**数える単位のキー列は、最後のGROUP BYまで殺さずに運ぶ**。

## ステップ3: 材料の最小粒度を決める

**やる作業**: 公式に当てはめるだけ。

> 材料の粒度 = 出力のD列がすべて決まり、かつ数える単位のキーが1行に1つ乗っている粒度

daily_kpisの場合: 日付・詳細タイプ・セグメントという3つのDは、どれも「あるユーザーのある日」につき1つに決まる属性。数える単位はユーザー。よって材料は **「ユーザー×日」の行**。

**成果物**: 材料テーブルの完成イメージ(この形を先に紙に書く):

| user_id | date | detail_user_type | past_d30_payment_segment | d1_access_flg | … | sales |
|---|---|---|---|---|---|---|
| 101 | 1/10 | 新規 | h_0円 | 1 | | 0 |
| 102 | 1/10 | 既存課金経験 | g_1円~1,000円 | 0 | | 800 |
| 103 | 1/10 | 既存課金経験 | g_1円~1,000円 | 1 | | 0 |
| 101 | 1/11 | 既存無課金 | h_0円 | 0 | | 0 |

この表が書ければ設計は終わりで、あとは「この表をどう作るか(ステップ4)」と「この表をどう畳むか(ステップ5)」しか残らない。

## ステップ4: その粒度で全材料を揃える

**やる作業**: ステップ3の完成イメージの各列に「どこから持ってくるか」を書き込む。持ってくる手段は3つしかない:

1. **JOINで持ってくる** — 同じグレイン(ユーザー×日)のモデル同士を `user_id, date` で結合
2. **CASEで導出する** — 既にある列を組み合わせて新しいラベルを作る
3. **ウィンドウで過去から持ってくる** — 過去30日売上のように「他の行」の情報が要るとき

### 出どころの探し方 — 列ごとに4つの質問を上から順に当てる

「どの手段を使うか」は考えるものではなく、材料表の列を1つずつ取り上げて固定の質問に答えるだけの機械的な作業にする。YESになったところで手段が確定する。

```
Q1. この列、既存のどこかのモデルに「そのまま」入っているか?
 ├ YES → そのモデルのグレインを確認:
 │        ・材料と同じ粒度(ユーザー×日) → そのままJOINで横に貼る
 │        ・材料より細かい(注文明細)    → 材料の粒度まで集計してからJOIN
 │        ・材料より粗い(ユーザー1行のマスタ) → JOINすると各行に配られる(マスタ参照)
 └ NO → Q2へ
Q2. 「同じ行の中にある別の列」だけから計算できるか?
 ├ YES → CASE / IF / 四則演算で導出(行の外を見ない)
 └ NO → Q3へ
Q3. 「同じテーブルの別の行」(過去・未来・同じユーザーの他の日)を見れば分かるか?
 ├ YES → ウィンドウ関数(LAG / LEAD / SUM OVER)
 └ NO → Q4へ
Q4. プロジェクトのどこにもない
 └ → データレイク(source)から新しいstagingを作って持ってくる
```

### Excelでイメージすると

材料表づくりはExcelのシートを埋める作業と同じ:

| SQLの手段 | Excelでいうと |
|---|---|
| 土台のFROM | まずA列・B列に行を並べる(user_id, date) |
| JOIN | **VLOOKUP** — 別シートからキーで引いてくる |
| CASE | 同じ行の中で完結する**IF式** |
| ウィンドウ | **上下の行を参照する式**(OFFSETや累計SUM) |

### 土台の選び方

FROMに置く土台は「**材料と同じグレインで、欲しい母集団の行を過不足なく持っているモデル**」を選ぶ。
daily_kpisなら母集団は「アクセスしたユーザー×日」で、`int__daily_registered_user_types` は**行が存在すること自体が『その日アクセスした』という事実**なので土台になれる。売上テーブルは購入した日しか行がないので土台にできない。

daily_kpisの各列の出どころ:

| 材料の列 | 出どころ | 手段 |
|---|---|---|
| user_id, date | int__daily_registered_user_types | 土台(アクセスした人×日が全行) |
| user_type, 各フラグ | int__daily_registered_user_types | 土台に含まれる |
| sales, payment_experience_flg, セグメント | int__daily_user_sales | ①JOIN(user_id+dateで⟕) |
| detail_user_type | user_type × payment_experience_flg | ②CASE導出 |

```sql
user_days as (
    select
        user_types.date,
        user_types.user_id,          -- ★数える単位のキーを殺さず運ぶ(ステップ2)
        case
            when user_type = '新規' then '新規'
            when user_type = '復帰' then if(payment_experience_flg = 0, '復帰無課金', '復帰課金経験')
            else                         if(payment_experience_flg = 0, '既存無課金', '既存課金経験')
        end as detail_user_type,     -- ②CASE導出
        user_sales.past_d30_payment_segment,
        user_types.d1_access_flg, ...,
        user_sales.sales
    from daily_registered_user_types as user_types
    left join daily_user_sales as user_sales   -- ①JOIN
        on user_types.user_id = user_sales.user_id
        and user_types.date = user_sales.date
)
```

**鉄則: このステップでは1行も増やさない・減らさない**。JOIN後に必ず確認する:

```sql
-- 土台と件数が一致すればJOINで行が化けていない
select (select count(*) from daily_registered_user_types),
       (select count(*) from user_days)
```

件数が増えたら「相手テーブルがJOINキーに対して一意でない」= 相手側のグレイン確定漏れ(distinct忘れ)を疑う。

### 演習例: 追加課題5(月次国別KPI)で4ルート全部を通す

材料の粒度=**ユーザー×月**として、列ごとに4つの質問を当てると:

| 材料の列 | Q1〜Q4の結果 | 手段 |
|---|---|---|
| user_id, month | `int__monthly_registered_user_types` がユーザー×月の行を過不足なく持つ | **土台** |
| その月の課金額 | Q1: `int__daily_user_sales.sales` にあるが**ユーザー×日**(材料より細かい) | **ユーザー×月に集計してからJOIN** |
| country | Q1: NO(リポジトリのどのモデルにもない)→ Q4: データレイクの `users` にある | **stg__users新設 → user_idでJOIN**(ユーザー1行のマスタ=材料より粗い→各行に配られる) |
| 国内/US/その他海外 | Q2: countryが行に乗った後なら行内で計算できる | **CASE導出** |

1つの課題で「そのままJOIN・集計してJOIN・新規source・CASE」の全ルートが出てくる。慣れるまでは、この表(列 × 出どころ × 手段)を**SQLを書く前に必ず埋める**こと。埋まらない列が「設計が終わっていない場所」であり、書き始めてから迷子になることがなくなる。

## ステップ5: 最後に一度だけGROUP BYする

**やる作業**: D列でGROUP BYし、ステップ2の表のとおりにメジャーを全部この1箇所で数える。

ステップ3のサンプル4行がこう畳まれる(1/10の3人 → グレイン2行):

| date | detail_user_type | segment | dau | d1_access_uu | sales |
|---|---|---|---|---|---|
| 1/10 | 新規 | h_0円 | 1 | 1 | 0 |
| 1/10 | 既存課金経験 | g_1円~1,000円 | **2** | 1 | 800 |
| 1/11 | 既存無課金 | h_0円 | 1 | 0 | 0 |

user_id 102と103は「同じ日・同じタイプ・同じセグメント」なので同じ行に畳まれ、dau=2になる——**グレインとは「誰と誰が同じ行に入るか」の決め事**だと、この変換を見れば分かる。

```sql
select
    date, detail_user_type, past_d30_payment_segment,   -- D列(=GROUP BYの軸)
    count(distinct user_id) as dau,                      -- M列(ステップ2の表のとおり)
    ...
    sum(sales) as sales
from user_days
group by date, detail_user_type, past_d30_payment_segment
```

## なぜ「最後に1回」なのか — 悪い例で見る

やりがちな失敗:「先に日付ごとの売上を集計しておいて、あとでユーザー行にJOINで配る」。

```
日次売上(先に集計): 1/10 → 800円
これをユーザー×日の3行(101,102,103)にJOINすると…

| user_id | date | daily_sales |
| 101     | 1/10 | 800 |  ← 102の売上が101にも乗る
| 102     | 1/10 | 800 |
| 103     | 1/10 | 800 |

最後にsum(daily_sales)すると 2,400円(正解は800円)
```

**途中でグレインを潰す→JOINで配る、をやった瞬間に多重カウントが始まる**。これが鉄則の理由:

> 集計は最後に一度だけ。途中でやりたくなったら、それは軸の粒度がまだ揃っていないサイン。

例外は「材料作りのための中間集計」のみ(しきい値判定用の別グレインUU集計、過去売上ウィンドウ等)。その場合も必ず明細に戻して(JOINして)からステップ5に合流する。`mart__monthly_department_brand_sales` のbrand_uu(その他判定)がこのパターン——UUを別グレインで数えるが、**結果はラベルの付け替えにだけ使い、売上の集計は最後の1回で行う**。

## 付与型のときはどうなるか

`int__daily_registered_user_types` で同じレシピを回すと:

- ステップ0: YAMLのカラムは user_id / date / user_type / 各フラグ。「数えた結果」の列がない → **付与型**
- ステップ1: 全列がD…ではなく、user_type・フラグは「1行に付く属性」。グレインは **ユーザー×日**(=出力1行はアクセスの事実そのもの)
- ステップ3: 材料の粒度=出力グレイン。**一致しているのでステップ5が消える**
- ステップ4がゴールになる: LAG/LEADで前後のアクセス日を持ってきて(手段③)、CASEでuser_typeとフラグを導出(手段②)して終わり

つまり付与型は「レシピの前半だけで完成するモデル」。型に関係なく変わらない核は:

1. **出力グレインを最初に宣言する**
2. **各CTEのグレインを常に一言で言えるようにする**(言えないCTEがあればそこがバグの温床)
3. **グレインを変えるのは意図した1箇所だけ**(集約型ならステップ5、付与型なら変えない)

過去に踏んだバグは全部この核に帰着する:
distinct忘れ=グレイン確定漏れ / ROWS・RANGE取り違え=材料の定義ミス / 途中集計をJOINで配る=グレインを変える場所が複数あった

## コメントテンプレート

レシピの答えをモデルファイルの冒頭に書いてから実装を始める:

```sql
-- 出力グレイン: 日付 × 詳細ユーザータイプ × 課金セグメント
-- メジャーの数える単位: ユーザー(dau, uu系) / 円(sales)
-- 材料の粒度: ユーザー×日
-- 材料の揃え方: int__daily_registered_user_types ⟕ int__daily_user_sales (user_id, date)
-- 集計: 最後に1回、3軸でGROUP BY
```

## このプロジェクトでの適用例

| モデル | 型 | ステップ3の粒度 | ステップ5の軸 |
|---|---|---|---|
| mart__daily_sales | 集約型 | 注文明細 | 日付 |
| mart__monthly_department_brand_sales | 集約型(+中間集計) | 注文明細(+ブランド付替え) | 月×タイプ×部門×ブランド |
| int__monthly_registered_user_types | 集約型 | ユーザー×日 | ユーザー×月 |
| mart__daily_kpis | 集約型 | ユーザー×日 | 日付×詳細タイプ×セグメント |
| int__daily_registered_user_types | 付与型 | ユーザー×日(=出力) | なし |
| int__daily_user_sales | ハイブリッド | ユーザー×日 | ①でGROUP BY→②③は付与 |

※ハイブリッド例の int__daily_user_sales は「①LEFT JOIN+GROUP BYで日次売上を確定(集約)→ ②ウィンドウで過去売上を付与 → ③CASEでセグメント判定(導出)」の3段。**グレインを変えるのは①の1箇所だけ**で、②③はユーザー×日を保ったまま。

## セルフレビューのチェックリスト

- [ ] 各CTEの**グレインを一言で言えるか**(CTEの直上に `-- グレイン: ユーザー×日` とコメントを書く習慣にする)
- [ ] GROUP BYは最後の1回だけか(途中集計があるなら「材料作り」として正当か、明細に戻しているか)
- [ ] JOINで行が増減しないか(土台と件数比較。相手テーブルはJOINキーに対して一意か)
- [ ] メジャーの数える単位のキー(user_id等)を最後のGROUP BYまで運んだか
- [ ] グレインの複合一意テスト・分類のaccepted_valuesテストを付けたか

## 関連する落とし穴(このプロジェクトで実際に踏んだもの)

- **UU(distinct count)は加法性がない** — 分類を付け替えたら必ず数え直す。UU同士を足してはいけない。ただし「同じ粒度の行を重複なく分割する軸」(1ユーザー1日1値の分類)で分けたUUは、合算すると全体UUに一致する(BIで再集約できる設計の根拠)
- **ROWSは行数、RANGEは値の距離** — 「過去30日」はカレンダー日なので `order by unix_date(date)` + `range between 30 preceding and 1 preceding`。ROWSだとアクセス日の飛びで窓がずれる
- **ウィンドウSUMのNULL** — 過去に行がなければ0ではなくNULL。`coalesce(..., 0)` で畳んでから判定しないと、セグメント誤分類やフラグ誤判定になる
- **`count(distinct ...)` はウィンドウ関数では使えない** — GROUP BYで先に数えてJOINで戻すのが定番の回避策
- **JOINの使い分け** — ファクトの必須構成要素(ヘッダ×明細)はINNER、ディメンション付与(マスタ参照)はLEFT。「相手が欠けたとき、行を消すべきか、NULLで残すべきか?」で判定する
- **`countif(条件)` は行数、`count(distinct if(条件, キー, null))` はユニーク数** — 別物
- **テーブルに並び順という概念はない** — CTE内のorder byは無意味。並びは読むクエリの最外側で指定する
