# 集計モデルの万能レシピ

dbtで集計モデル(mart・集計系intermediate)を作るときに、SQLを書き始める前に必ず回す5ステップの手順。
このレシピの答えをコメントとしてモデルファイルの冒頭に書いてから、実装を始めること。

## 5ステップ

### ステップ1: 出力のグレインを宣言する

- YAML(メタ情報)のカラムを**ディメンション**と**メジャー**に仕分けする
- **グレイン = ディメンション列の全部の組み合わせ**。「1行=何か」を一言で言えるようにする

| 種類 | 役割 | 見分けるヒント |
|---|---|---|
| ディメンション(軸) | 行を「どう切るか」 | STRING型・DATE型、値が分類やラベル |
| メジャー(指標) | 行ごとに「何を数えるか」 | 数値型、名前が `~uu` / `~count` / `sales` など |

> ディメンションは集計関数で「潰せない」。潰せない列がテーブルにあること自体が、その列がグレインの一部である証拠。

### ステップ2: メジャーの「数える単位」を特定する

- UU系 → **ユーザー**を数える
- 売上系 → **円**を足す
- ここから「集計直前の材料は何単位の行でなければならないか」が逆算できる

### ステップ3: 材料の最小粒度を決める

- 出力グレイン+数える単位から、集計直前に必要な粒度が決まる
- 例: 日次KPI(日付×詳細タイプ×セグメント、UUを数える)→ 材料は「ユーザー×日」

### ステップ4: その粒度で全材料を揃える

- 同じグレイン同士のモデルをJOINし、軸ラベル(分類など)をCASEで導出する
- **ここではまだ1行も潰さない**

### ステップ5: 最後に一度だけGROUP BYする

- 軸でグルーピングし、メジャーを全部この1箇所で数える

## 鉄則

> **集計は最後に一度だけ。途中でやりたくなったら、それは軸の粒度がまだ揃っていないサイン。**

- ❌ 「日付単位で先に集計してJOINで各行に配る」→ 多重カウントの温床
- ✅ 「材料を揃えてから、最後に集める」
- 例外は「材料作りのための中間集計」(しきい値判定用の別グレイン集計、過去売上のウィンドウ等)のみ。それも必ず明細に戻して(JOINして)からステップ5に合流する

## このプロジェクトでの適用例

| モデル | ステップ3の粒度 | ステップ5の軸 |
|---|---|---|
| mart__daily_sales | 注文明細 | 日付 |
| mart__monthly_department_brand_sales | 注文明細(+ブランド付替え) | 月×タイプ×部門×ブランド |
| int__monthly_registered_user_types | ユーザー×日 | ユーザー×月 |
| mart__daily_kpis | ユーザー×日 | 日付×詳細タイプ×セグメント |

## コメントテンプレート

モデルファイルの冒頭にこれを書いてから実装する:

```sql
-- 出力グレイン: 日付 × 詳細ユーザータイプ × 課金セグメント
-- メジャーの数える単位: ユーザー(dau, uu系) / 円(sales)
-- 材料の粒度: ユーザー×日
-- 材料の揃え方: int__daily_registered_user_types ⟕ int__daily_user_sales (user_id, date)
-- 集計: 最後に1回、3軸でGROUP BY
```

## セルフレビューのチェックリスト

- [ ] 各CTEの**グレインを一言で言えるか**(言えないCTEがあればそこがバグの温床)
- [ ] GROUP BYは最後の1回だけか(途中集計があるなら「材料作り」として正当か)
- [ ] JOINで行が増減しないか(相手テーブルはJOINキーに対して一意か)
- [ ] メジャーの数える単位のカラム(user_id等)を材料CTEに持ち込んだか
- [ ] グレインの複合一意テスト・分類のaccepted_valuesテストを付けたか

## 関連する落とし穴(このプロジェクトで実際に踏んだもの)

- **UU(distinct count)は加法性がない** — 分類を付け替えたら必ず数え直す。UU同士を足してはいけない。ただし「同じ粒度の行を重複なく分割する軸」(1ユーザー1日1値の分類)で分けたUUは、合算すると全体UUに一致する(BIで再集約できる設計の根拠)
- **ROWSは行数、RANGEは値の距離** — 「過去30日」はカレンダー日なので `order by unix_date(date)` + `range between 30 preceding and 1 preceding`。ROWSだとアクセス日の飛びで窓がずれる
- **ウィンドウSUMのNULL** — 過去に行がなければ0ではなくNULL。`coalesce(..., 0)` で畳んでから判定しないと、セグメント誤分類やフラグ誤判定になる
- **`count(distinct ...)` はウィンドウ関数では使えない** — GROUP BYで先に数えてJOINで戻すのが定番の回避策
- **JOINの使い分け** — ファクトの必須構成要素(ヘッダ×明細)はINNER、ディメンション付与(マスタ参照)はLEFT。「相手が欠けたとき、行を消すべきか、NULLで残すべきか?」で判定する
- **`countif(条件)` は行数、`count(distinct if(条件, キー, null))` はユニーク数** — 別物
- **テーブルに並び順という概念はない** — CTE内のorder byは無意味。並びは読むクエリの最外側で指定する
