# update-docs

コード変更内容を分析し、README.md と CLAUDE.md の更新が必要かを判断・更新する。コード変更後やコミット前に呼び出して、ドキュメントの陳腐化を防ぐ。dbtモデルの追加・削除、設定変更、スキル追加など、ドキュメントに影響する変更があった場合に使用する。

また、変更がなくてもドキュメントの記述が実態と乖離していないか検証する機能も持つ。定期的に呼び出して、ドキュメントの正確性を保つ。

## 手順

### 1. 動作モードの決定

以下を並列で実行して、未コミットの変更があるかを確認する：
- `git diff HEAD` — 未コミットの変更
- `git diff --cached` — ステージ済みの変更
- `git log --oneline -5` — 直近コミット（最近の変更の流れを把握するため）

**変更がある場合** → **差分モード**（ステップ2へ）
**変更がない場合** → **検証モード**（ステップ3へ）

---

## 差分モード（コード変更に伴うドキュメント更新）

### 2. 差分ベースの更新判断

Read ツールで README.md と CLAUDE.md の内容を読み込み、変更内容とドキュメントの記述を照合して更新が必要かを判断する。

**CLAUDE.md — 開発者向けの技術リファレンス**

更新が必要：
- モデルディレクトリ構成の変更（`models/` 配下のレイヤー追加・再編、命名規則の変更）
- `dbt_project.yml` の変更（profile名、マテリアライズ設定、各種パスの変更）
- `packages.yml` による依存パッケージの追加・削除（`dbt deps` が必要になる等、開発フローに影響する場合）
- 開発環境の変更（venvの場所、dbtバージョン、アダプタ、profiles.ymlの前提）
- よく使うコマンドの変更（新しく必要になった/不要になったdbtコマンド）
- 設計上の重要な意思決定
- スキル（スラッシュコマンド）の追加・変更・削除

**README.md — ユーザー向けの利用ガイド**

更新が必要：
- ハンズオンの流れや前提条件の変更
- セットアップ手順の変更（venv構築、profiles.ymlの設定、認証方法）
- 実行するコマンドの変更（`dbt run` / `dbt test` 以外の手順が増えた場合等）
- 扱うデータの変更（seedsの追加、参照するBigQueryデータセットの変更）

**更新不要と判断してよいケース：**
- モデルSQL内部のロジック修正のみ（構成・使い方が変わらないもの）
- 動作が変わらないバグ修正
- 外部インターフェースに影響しない内部リファクタリング
- コメント・ドキュメント内の誤字修正のみ

迷ったら「不要」寄りに判断する。ドキュメントの過剰な更新はノイズになる。

→ ステップ5（更新案の提示と確認）へ

## 検証モード（ドキュメントと実態の整合性チェック）

### 3. ドキュメントとソースの読み込み

以下を並列で読み込む：
- README.md
- CLAUDE.md
- `dbt_project.yml`
- `packages.yml`（存在する場合）
- `models/` 配下のディレクトリ構成と `schema.yml`
- `.claude/skills/` 配下のスキル定義ファイル一覧
- `.claude/settings.json`（有効化プラグイン等）
- `.github/workflows/` 配下のワークフローファイル（存在する場合）

### 4. 整合性チェック

ドキュメントの記述を、実際のファイル内容と突き合わせる。以下のチェックリストに沿って不整合を探す。

**CLAUDE.md のチェック項目：**

| チェック対象 | 照合先 | 確認内容 |
|---|---|---|
| ディレクトリ構成の説明 | 実際の `models/` `seeds/` `macros/` 等 | 記載ディレクトリ・レイヤー構成が実態と一致するか、未記載の構成要素がないか |
| マテリアライズ設定の記述 | `dbt_project.yml` の `models:` 設定 | view/table等の記述が実際の設定と一致するか |
| profile名の整合性 | `dbt_project.yml` の `profile:` と `~/.dbt/profiles.yml` | プロファイル名が一致しているか（不一致なら `dbt run` が失敗する） |
| 環境の記述 | `venv/` の実態（dbtバージョン・アダプタ） | 記載のdbtバージョン・アダプタが実際のインストールと一致するか |
| よく使うコマンド | dbtプロジェクトの実態 | 記載コマンドが現在の構成で実行可能か（seeds無しで `dbt seed` を案内していない等） |
| Gitワークフローの記述 | `.claude/settings.json` と `.claude/skills/` | 記載スキル（git-workflow:commit 等）が実際に利用可能か |
| CI/CDセクション | `.github/workflows/*.yml` | トリガー条件・ステップ・必要なSecrets名が実態と一致するか（セクションがあれば） |

**README.md のチェック項目：**

| チェック対象 | 照合先 | 確認内容 |
|---|---|---|
| 記載コマンド | dbtプロジェクトの実態 | `dbt run` / `dbt test` 等の案内が現在の構成で動作するか |
| セットアップ手順 | venv・profiles.ymlの前提、`packages.yml` | 手順通りに進めて正しく動作する記述か（`dbt deps` の要否等） |
| モデル・データの説明 | `models/` `seeds/` の実態 | 説明されているモデルやデータが実在するか |

不整合が見つからない場合は「README.md / CLAUDE.md の記述は実態と整合しています」と伝えて終了。

→ ステップ5（更新案の提示と確認）へ

## 共通ステップ

### 5. 更新案の提示と確認

更新が必要と判断した場合、AskUserQuestion ツールで更新内容を提示し確認を取る：

- 質問文に、どのファイルのどの箇所をどう変更するかを具体的に記載する
- 選択肢: ["更新する", "スキップ"]
- README.md と CLAUDE.md の両方に更新がある場合でも、1つの質問にまとめてよい

更新が不要と判断した場合は理由を伝えて終了。

### 6. 更新の実行

ユーザーが「更新する」を選んだ場合のみ、Edit ツールで該当箇所を更新する。

- 既存のスタイル・トーン・構造を維持する
- 変更に関係する箇所だけを編集する（全体の書き換えはしない）
- 推測で書かない。コードから読み取れる事実のみを記述する

### 7. 結果の報告

更新した場合は、変更箇所を簡潔に報告する。`/git-workflow:commit` 等の他スキルから呼ばれている場合は報告後に制御を返す。
